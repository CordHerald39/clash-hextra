对照 Clash（mihomo）有无 `no-resolve` 时，应把配置行的差异映射到官方匹配行为，再用实际命中的规则类型来验证，而不是臆造日志关键字。本页给出的是规则语法与附加参数语义，没有规定日志字段名；因此“对照日志”是对照“是否为检查目标 IP 而发生解析、以及最终落在哪一类规则”，配置差异则必须能在 `rules` 原文里逐字看到。

## 适用条件

对照对象应是同一条目标 IP 规则的两种写法：带 `no-resolve` 与不带。文档示例为 `IP-CIDR,127.0.0.0/8,DIRECT,no-resolve`。可对照的类型限于关于目标 IP 的规则：`IP-CIDR`、`IP-CIDR6`（效果相同的别名）、`IP-SUFFIX`、`IP-ASN`、`GEOIP`。请求需以域名进入匹配，否则文档所述“域名开始匹配关于目标 IP 的规则时将触发 DNS 解析”不构成对照差。列表其余部分、出站名、`src` 是否同时出现，必须保持不变，否则无法把结果差异单独算给 `no-resolve`。

## 先对照配置再对照命中结果

配置侧逐项核对：

1. 参数是否写在出站名称之后，与示例同构。
2. 类型是否确为目标 IP 类；`DOMAIN`、`GEOSITE`、`MATCH` 等即使被改写，也不能当作本参数的对照样本。
3. 该条上方有没有更早的目标 IP 规则。官方说明：更早的匹配若已触发 DNS 解析，则依旧会匹配到带 `no-resolve` 的目标 IP 类规则。对照表里要单列“第一条可能触发解析的规则”和“被开关该参数的规则”的前后关系。
4. 逻辑规则 `AND`/`OR`/`NOT` 若包裹了目标 IP 条件，先按文档核对括号和 payload，再决定对照的是内层哪一条。`RULE-SET` 要对照集合内部各行，而不是只看引用名。

命中结果侧：无该参数时，域名走到该条应允许为检查目标 IP 而解析，从而可能命中 CIDR/ASN/GEOIP；有该参数且此前从未解析时，该条缺少可供比对的目标 IP，请求应继续向下，可能落到后续域名规则或最后的 `MATCH`。若两种配置最终出站相同，优先用“更早已解析”或“根本没走到该条”解释，而不是判定参数没写上。

## 日志侧能对上什么、不能对上什么

本页未定义日志格式，因此不能用自拟的解析成功/失败文案当判断依据。可对照的只有与规则语义直接对应的事实：匹配是否发生在目标 IP 类规则、该规则行是否含 `no-resolve`、其上方是否存在可触发解析的同类规则。来源 IP 类（`SRC-IP-CIDR`、`SRC-GEOIP` 等）和端口、进程、入站类规则不参与“为检查目标 IP 而解析”的对照。`src` 会把目标 IP 匹配转为来源 IP 匹配，日志里若反映的是来源条件，应单独列为另一对照项，避免与 `no-resolve` 混读。

## 对不上时下一步

若配置已改、命中规则类型却完全不变，下一步检查请求是否从未到达该行（上方 `DOMAIN`/`GEOSITE` 已命中），或上方未带 `no-resolve` 的目标 IP 规则已经触发过解析。若有记录但无法区分“跳过解析”与“解析后未落入 CIDR”，不要增加无关类型，而是把该条上下各一条目标 IP 规则纳入同一张对照表，严格按从上到下的优先级重走一遍。逻辑规则括号错误、集合内外参数不一致时，先把配置改到与文档示例同构，再重新对照。
