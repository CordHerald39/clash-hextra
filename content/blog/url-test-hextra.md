要把同一时间各节点的测试条件记录下来以便对照，手册并没有单独的快照字段。能够写入配置并在日后复现的，是健康检查相关通用字段：url、interval、timeout、expected-status、lazy、max-failed-times，再加上检查范围声明——只会检查 proxies 里的代理，不会检查 use 引入的代理集合。所谓记录，是记录如何测、测谁、何时测，不是本页未提供的全员延迟表。下面说明适用条件、应把哪些条件写进文本，以及无法得到同一时刻结果时下一步。

## 适用条件

本方法适用于你能保存 proxy-groups 文本，并且关心的是健康检查如何执行。name 与 type 必须存在，名称含特殊符号应当用引号包裹，否则条件无法对应到确定的组。若组当前未被选中，lazy 默认为 true，未选择到当前策略组时不进行测试，各节点并不处于同一周期正在检查的状态。interval 为 0 则不启用定时测试，没有统一节拍。节点若只通过 use 引入，则不在该组 url 的检查名单中，只记录地址不会覆盖它们。filter、exclude-filter、exclude-type 会改变谁进入列表，exclude-type 不支持正则、用竖线分割、仅排除引入的出站代理且无视大小写；记录条件时必须连同这些规则一起保存。include-all、include-all-proxies、include-all-providers 按名称排序引入且不含策略组，名单本身也是条件的一部分。

判断一套条件能不能拿来做同一时刻对照，依据是：探测地址相同、超时相同、期望状态码语义相同、间隔相同、懒惰行为相同、失败次数阈值相同，并且被比较的名称都在 proxies 里。缺了范围声明，只抄地址，对照会失真。

## 把同一套条件写进配置

第一步，固定 url 为同一健康检查测试地址，手册示例采用 generate_204 一类探测，保证比较的是同一目标。第二步，固定 expected-status。默认星号表示对响应状态不做要求；若要同一时刻用同一可用标准，应显式写出状态码，可用斜线与范围，如 200/302、400-503 或混合写法。第三步，固定 timeout，单位毫秒，作为统一超时。第四步，固定 interval，单位秒，非 0 才有定时节拍。第五步，写下 lazy 的取值，避免事后才发现未选中的组根本没测。第六步，写下 max-failed-times，默认 5，超过则触发一次强制健康检查，这会影响你看到的是否为强制刷新后的结果。第七步，列出当时 proxies 中的名称，不要只用 use 里的集合名代替。第八步，一并记录筛选与 include 开关。完成以上文本后，才能在另一时刻用同一套方式复现检查。手册没有要求把每次探测数值存进这些字段，因此记录的是条件而不是结果数字。default-selected 与 empty-fallback 分别管默认选择和空组回退，不要写进测试条件清单。hidden 与 icon 只服务 API 展示。disable-udp 只关闭该策略组 UDP，同样不是测试条件。

## 无法同时得到结果时下一步

若希望同一秒看到所有节点的检查，但有的有结果、有的没有，按手册找原因。先看 lazy：未选中的组默认不测，下一步是让该组处于被选择状态，或不再假设它与其它组对齐。再看节点位置：use 引入的集合不会被该 url 检查，下一步把要比对的出站写进 proxies。再看 interval 是否为 0、timeout 是否过短、expected-status 是否把本应接受的状态码判失败。max-failed-times 未达到时可能尚未强制再测。不要用已弃用的 interface-name、routing-mark 充当测试记录；这两项应写在代理节点上，优先级为代理节点大于代理策略大于全局，与如何记录检查条件无关。若名单被筛选改变，对照当时的正则与类型排除。配置里能复现的只有上述条件；本页未给出导出同一时刻全员延迟的字段，失败后应逐项核对条件，而不是添加未记载的采集步骤。
